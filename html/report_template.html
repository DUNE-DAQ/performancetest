Readout System Performance Test: &run-&topology
Purpose: &purpose
Definitions: Abbreviations:
  • RU - Readout Unit: The COTS server that runs the Readout subsystem
  • NIC - Network Interface Controller
  • NUMA - Non-Uniform Memory Access: Usually used in testing multi socket systems, where each CPU has its own memory region
  • APA - Anode Plane Assembly
  • CRP - Charge Readout Plane
  • SNB - Supernova Burst
  • KPI - Key Performance Indicator: The set of metrics and their relation that we make our analysis and fail/pass scenarios on.
Readout System Components:
  • Readout Data Type: Adapter types/structures of detector data frames
  • Data Reception: Receives data from the high-speed I/O device. (Corresponding DAQ plugin: NICReceiver)
  • Processing Pipeline: Data integrity check pipeline stages before buffering
  • Trigger Primitive Generation - TPG: The most important computing intensive processing stage is executed on every received data frame, and extracts activity from the frames. The extracted data is sent out to the backend network. The process must be efficient in ordering and distribution to aid the performance of the downstream subsystems. (E.g.: Trigger, Dataflow)
  • Latency Buffer: Software containers that buffer data for several seconds in the host RAM
  • Request Handling: Software component that extracts requested data from the latency buffers and sends the extracted data to the backend network. It also ensures that old, non-requested data is periodically discarded from the latency buffers.
  • SNB Store: Software component and local high-speed storage media on the RU, that persists data for continuous 100 seconds to the storage media.

Test Type: Baseline Testing

Process for evaluating a system or its component's initial performance and characteristics.

For the Readout System and the Readout Unit, this includes all the components operating in parallel. (Peak utilization with all functionalities active.)

Failure Criteria:

A test run will be considered “failed” if any of the following conditions are met:

Readout Component Failures:

  • Data Reception failure:
    • Continuous occurrence of missed or dropped packets
      • (Reconsider configuration adjustments and re-run the test.)
  • Trigger Primitive Generation failure:
    • Frequent error messages about post-processing not keeping up.
      • (Reconsider allocating more resources to the component and re-run the test.)
  • SNB recording failure:
    • At the end of the 100s recording test, if the recorded data size on the fast storage doesn't match the expected value
      • For a single APA for 100 seconds.
      • For a single CRP for 100 seconds.
    • Recorded file sizes are zero
    • Recorded file sizes are not matching in size

Excessive system utilization:

  • CPU utilization:
    • Any CPU core on the system is above avg. 80% utilization during the test
  • Memory bandwidth utilization:
    • Any NUMA node bandwidth is above avg. 80% utilization during the test
These constraints are introduced in order to avoid artifacts and resource utilization spikes that might hinder deterministic performance characteristics of the readout applications on the target RU.

Post-Test Analysis:
Data collection:

The test aims to measure the resource utilization footprint of the application running on the target RU during the test, with their configuration in terms of topology and hardware usage claim. The RU should be employed with hardware and kernel observability tools in order to capture the following metrics:

Overall RU utilization in terms of:
  • CPU instructions per second and percentile per core
  • Memory BW utilization per channel
  • CPU cache utilization in terms of misses and hits
Every application and their threads' utilization in terms of:
  • Peak and average CPU percentile
  • Peak and average memory BW utilization
  • Peak and average CPU cache utilization in terms of misses and hits
Application and system profiler summary:
  • uProf, vTune, gProf, etc. or any other non-architecture specific profiler output for the application during the test must be available for further analysis.

Data collections should be centralized in the available hardware apparatus. If this is not feasible, reports in terms of plain text or CSV files can be used to generate reports on the KPIs and cross-metric evaluations.

Reporting:

The raw data collected is shown in plots as shown in the grafana monitoring page:

  • trigger_primitive.pdf : Information regarding the TPG. This information is processed to create the key parameters of interest:
    • Hit rate (transmition)
  • resource_utlization.pdf: Information from the node exporter dashboard and intel PCM dashboard. The data is performance metrics of the readout host machine, the key parameters of interest created from this information are:
    • CPU utilization (total, per core and per thread if the CPU pinning file is documented).
    • Total memory bandwidth, and memory bandwidth per NUMA (for Intel machines only).
    • Network transmission, receiving rates.
    • SNB Recording time.
    • RAID array write rate.
    • RAID array total written to disk.
  • frontend_ethernet.pdf: Informatio from the frontend readout, regarding data received from the NICs and data transmitted. The key parameters of interest calculated with this data are
    • Data Input from the 12x10G links.

The key parameters of interest calculated from the raw data are shown in the following documents:

  • cpu_plots.pdf : Shows the CPU utilization overall, per core, and per thread. This allows one to assess the overall CPU utilization for the duration of the test, as well as which processes used the most CPU time. This information is used to check the failure criteria that the total CPU usage on average should be below or at 80%. This is indicated by the 50% percentile CPU usage and the 90% and 99% percentiles shown alongside this to highlight fluctuations in the CPU usage for the duration of the test.
  • memory_plots.pdf : Shows the total system memory usage, which should be below 80% for the duration of the test.
  • disk plots.pdf : Shows the key parameters of interest for the SNB tests. Specifically, this is the disk IO time, disk write rate, and total data written to disk for each RAID array and specific NVMe. The disk IO time should be equal to the acceptance value (100s), while the disk rate should at minimum be the data input rate for the specific anode plane or the RAID array write rate. The total data written to disk for a single RAID should exceed the acceptance criteria and be at or below the benchmark value for the specific wire plane. For each key parameter mentioned, the rate over time as well as the total value across the whole test is shown in the plots.
  • tp_plots.pdf : Shows the rate of TPs generated by the TPG, as well as the rate of TPs received and written by the TP writer, both per APA/CRP and detector. This is compared to the hit rate defined in the acceptance criteria, where the expectation is that the TP rate should be above the baseline TP rate and, if possible, exceed the benchmark hit rate. In addition, the number of requests handled and the number of TPs dropped during transmission are shown to ensure there are no errors with transmitting the TPs. The total number of TPs dropped should be zero. In addition, the number of "bad", "old window" and "timing out" requests should be kept to a minimum (<1%).
  • fe_plots.pdf : Shows the data input as the data received by the readout machine across the whole detector and per anode plane. These are compared to the data input rate as calculated in the acceptance criteria. In addition, the number of packets with various error types is also shown to check that no errors occurred while the ADC data was received. These should all be kept to a minimum (<1%).
  • re_plots.pdf : Shows the request handling rate and the total requests for the ADC readout, such that the "bad", "old window" and "timing out" requests can be assessed. These should be kept to a minimum (<1%).
  • ov_plots.pdf : Shows the global trigger rate and the amount of rate data written by Dataflow during the test.
  • network_plots.pdf : Shows the data rate received and transmitted by the readout server for each device, as well as the total amount received and transmitted during the test. The data received indicates how much data is being received from external sources, while the data transmitted shows how much and how fast data is being transmitted from the readout machine to Dataflow.
